## The gates, in full — this list is complete, nothing else is expected of you

The previous wave was sent back because the brief omitted the linter. It is here now:

```bash
gofumpt -w <your packages>
go vet ./internal/<yours>/...          # type-checks _test.go; `go build` does not
golangci-lint run ./internal/<yours>/...
go test ./internal/<yours>/ -race -count=1
```

All four clean before you print your sentinel. `golangci-lint` runs `gosec` and `govet`
with `shadow`: a shadowed `err` in non-test code may be a real defect, so read both
declarations before renaming anything, and say in your report whether any was real. A
suppression is `//nolint:<linter> // <reason>` with the reason written out. **Never weaken
a test to satisfy a linter** — if a check and an assertion genuinely conflict, stop and say
so.

## The scenario, exactly

1. The spec starts **its own local HTTP test server**. It does not reach the network.
2. A Postman v2.1 export carrying `{{baseUrl}}/users` and a bearer token is imported
   **through the UI**, not by calling a client from the test.
3. **A walk of every file under the collection root finds neither the secret value nor any
   vault identifier.** This is design §8 and it is the assertion the whole format exists
   for — write it as a filesystem walk, not as a check of one file.
4. The request opens, **Send is pressed**, and a run appears with `201` and the decoded body.
5. **Raw is opened, and the token appears as a badge naming the secret — never as its
   bytes.** Assert the bytes are absent from the DOM, not merely that a badge is present.

## The rules that decide whether this test is worth having

- **Wait on observable state, never on a duration.** A run row, a DOM state, a file on disk.
  A spec that needs a slow machine to pass is broken on a fast one too; it has only not been
  caught yet. There is no `waitForTimeout` in this file.
- **Drive the seams a person reaches.** A test written by calling the client proves the
  client works, not that a person can do this. The connection manager shipped with no way to
  create a group while 1041 tests were green, every one of them mounting a component and
  asserting what it rendered.
- Run it in the container: `PW_PROJECTS=chromium e2e/run-in-container.sh e2e/api-testing.spec.ts`.
  **The container's failure set is not CI's** — it is Linux WebKit at a container-default
  viewport. If something fails only there, investigate which one is lying before "fixing" it.
