## What shipped

Readiness for the assistant used to ask "is an endpoint configured". So an
endpoint with a valid key reported **"Ready"** while the `answering` role had no
model, and the refusal arrived at the person's first question. It now asks
whether the role RESOLVES, using the refusal vocabulary `profile.ResolveRole`
already returned and nobody had put on the wire.

Seven planned tasks plus two fixes, ten commits, 38 files, +3819/−321:

- **`profile.DefaultModel`** — one user-authored `(endpoint, model)` pair that
  every role without its own assignment resolves through. A new INPUT to
  `ResolveRole`, never a second resolver (AD-8).
- **`agent.status` grows `answering`** — `ready` plus one of six reasons.
  Endpoint and credential stopped being the headline and became reasons a role
  cannot resolve.
- **The ladder** (`frontend/src/agent-status-line.ts`) — each unready state has
  one sentence and one repair page. Copy is exact and is reused verbatim by two
  surfaces; do not reword it in one place.
- **The chip** (`editor.ts` + the new `frontend/src/agent-readiness.ts`) — Ask
  mode only, naming the model that will answer. Provider → Endpoints, model →
  Roles.
- **The Roles page** — a default control above the roles, "As default" as each
  role's initial value, and a status line that stops repeating the two selects
  above it.

`e2e/assistant-readiness.spec.ts` watches the whole path. Its load-bearing
assertion is the MIDDLE one: after an endpoint with a valid key is added, the
chip reads _Choose a model_ and **not** anything resembling ready.

## The default does not violate `nocx-e6kn2`, and here is why it does not

That closed decision forbids "a silent fallback to some other model — a person
cannot tell which model answered". A reviewer argued this branch breaks it and
that the decision must be reopened. **It does not, and the evidence is in the
tree:** `content.RunFacts` (`internal/content/ledger.go:703`) persists
`EndpointID` and `Model` per run, and `frontend/src/agent-ask.ts:241` sets
`dataset.answeredBy`, in a comment citing that bead by name.

The forbidden thing is the PRODUCT choosing on someone's behalf. This is the
product using a choice the person made once. If you are about to re-litigate
this, read those two lines first.

What survives of the objection is `nocx-4k1r6`: the attribution is a data
attribute, not visible text.

## Two defects this found in code that was already merged

Both came from the PLAN, not from the implementers — the workers reproduced the
plan faithfully. Both are fixed and the plan is corrected to match (`52aed9ab`,
`c58cc0b3`).

**The credential was computed across the whole endpoint fleet.**
`handleAgentStatus` reported `resolvable` if ANY endpoint's credential
resolved, so a deleted key on the endpoint that would answer read as ready
whenever some unrelated endpoint was healthy. That is the same lie as
readiness-from-endpoint-existence, one level down, and it survived the design
review because the spec and the plan both wrote "the credential" as though
there were one.

**`no-models` shadowed the two specific refusals.** A default naming a deleted
endpoint reported _"that endpoint offers no models"_ whenever the surviving
endpoint happened to be empty — two states, one message, pointing at the wrong
page. Precisely the failure the ladder was built to prevent. `no-models` is now
reachable only inside the unassigned arm: nothing selected AND nothing to
select.

## Traps for whoever picks this up

**The status line is SILENT on purpose.** A role that resolves to exactly what
its two selects show renders no sentence at all. This already broke a shared
fixture: `agent-ask.spec.ts` waited for that line and went red in both browsers
(fixed in `0d4cefc0` by reading the selects instead). If another spec or
surface waits for it, that is the same defect, not a regression to revert.

**Run e2e in the container BEFORE `make ci`, or after cleaning up.** The
container leaves `.e2e/home` owned by root; `gofumpt -l .` then dies with
`permission denied` and it reads like a lint error in your code. `.e2e/` is
gitignored so nothing surfaces it. Filed as `nocx-9ycb3`.

**The chip refreshes on entering Ask and on the pane becoming visible**, not on
Settings-side writes — those happen in another pane. Same outcome for a person
walking the normal path; a chip can lag if Settings and the terminal are
visible side by side. Deliberate, stated in the PR, not yet a bead.

**`roles.setDefault` validates and writes inside the store's critical section**,
against one loaded document. `roles.assign` deliberately does NOT validate that
the endpoint exists — a dangling assignment is a feature (the person is
entitled to be told their choice broke). Do not "fix" the asymmetry; it is
argued in the plan's Task 2.
