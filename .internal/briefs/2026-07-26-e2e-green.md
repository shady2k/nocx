## What "green" means here, and what it does not

- A test that fails because the **product** is wrong: fix the product, or if the fix is larger than
  this task, file it in your report and say so plainly. Do not weaken the assertion to make it
  pass.
- A test that fails because the **selector or flow is obsolete** after the refactor: update it to
  the current DOM. The tab button is no longer built where it used to be; read `tab-strip.ts` for
  the real structure rather than guessing.
- A test that is **flaky** rather than failing: five flakes are filed separately (`nocx-9ci`,
  `nocx-heq`, `nocx-epm`, `nocx-qkp`, `nocx-zaj`) and are **not yours**. If you can see the cause
  cheaply, say so in your report and move on; do not fix them here.
- **Never delete a test to make the suite green.** If a test covers a feature that was removed by
  design, deleting it is correct — but say which feature, which commit removed it, and why the
  test has no subject any more. That standard was set earlier on this programme: one test was
  deleted because the feature was genuinely gone, and a sibling was deliberately kept because it
  was the only evidence of a real defect.

## Two things that will save you an afternoon

**Read the memories before fighting the environment:** `bd memories e2e`. There is a headless path
that needs no wails, no GTK and no display — `cmd/devharness` plus the `NOCX_WS_PORT` shim in
`e2e/harness.ts`. Someone previously burned a session on Xvfb, EGL errors and NixOS rebuilds
before discovering it. You are told not to run `bd` commands, so treat this as: **read
`e2e/harness.ts` and `cmd/devharness` first**, and use that path.

**Terminal output is not in the DOM.** xterm.js renders to a WebGL canvas, so you cannot assert on
terminal text with a DOM locator. Assertions must go through the harness or through DOM elements
the app itself creates (blocks, gutter glyphs, tab titles).
