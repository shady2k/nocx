# `.beads/issues.jsonl` уходит из git; страховку публикует `pre-push`

Дата: 2026-08-29
Статус: спека, утверждена владельцем; план — следующим шагом

## Проблема

`.beads/issues.jsonl` конфликтует почти в каждом PR на GitHub.

Причина механическая и полностью подтверждена измерением на PR #129
(`fix/live-screen-capture-bounded` → `fix/tui-summon-stop-recovery`):

- `.githooks/pre-commit` шаг 7 (`export_beads_snapshot` в `.githooks/beads-hook.sh`)
  перегенерирует файл и делает `git add` на **каждом** коммите. Значит его
  трогает каждая ветка, всегда: 2707 строк, 6.6 MB, переписываются целиком.
- Локально конфликт уже решён: `nocx-prz9` (PR #85) поставил merge driver
  `merge.beads-export.driver = bd export -o %A`, и он работает —
  `git merge-tree --write-tree` для веток PR #129 проходит чисто и печатает
  `Exported 2711 issues`.
- **GitHub кастомные merge drivers не запускает никогда.** Драйвер — это
  per-clone git config, git его не переносит и сервер о нём не знает. Тот же
  `merge-tree` с `-c merge.beads-export.driver=false` даёт ровно один конфликт:
  `.beads/issues.jsonl`. Это и есть `mergeable: CONFLICTING` на PR #129.

Второй множитель: мержи в `main` идут кнопкой на GitHub («Merge pull request
#131», «#133»), поэтому локальный хук на `main` не срабатывает вовсе. Отсюда
ручные коммиты вида `bc43293c chore(beads): regenerate the export after merging
main`.

Вывод: драйвером эта половина не чинится в принципе. Либо файла нет в диффе
ветки, либо его нет в git.

## Решение

Убрать файл из git и заменить его страховку рефом, который публикует `pre-push`.

### 1. Что уходит из git

- `.beads/issues.jsonl` → строка в `.gitignore`, затем `git rm --cached`.
- `.gitattributes`: строка `.beads/issues.jsonl merge=beads-export` и весь
  предшествующий ей комментарий удаляются. Если после этого в файле не остаётся
  ни одного правила — удалить файл целиком.
- `Makefile`, цель `hooks`: убрать две строки `git config merge.beads-export.*`,
  добавить `git config --unset merge.beads-export.driver` и
  `--unset merge.beads-export.name` (обе с `|| true`), чтобы вычистить уже
  настроенные клоны. Поправить комментарий на `Makefile:176`.
- `.githooks/pre-commit`: шаг 7 удаляется вместе с `ok "beads export"`.
- `.githooks/beads-hook.sh`: `export_beads_snapshot` удаляется — у неё не
  остаётся вызывающих.

Побочные выигрыши, оба измеримые: коммит перестаёт ждать экспорт 6.6 MB, и файл
перестаёт блокировать `git checkout` — та боль, что записана в
`.internal/HANDOFF-2026-08-18.md:95`.

### 2. Чем заменяется страховка

`nocx-wj4` — единственный аргумент за то, чтобы копия бэклога лежала в
git-объектах: параллельные пуши в git-protocol Dolt remote могут подвесить
историю, и тогда копия внутри git — всё, что остаётся.

Страховку публикует `.githooks/pre-push` git-плюмбингом, не касаясь рабочего
дерева и индекса:

```sh
blob=$(bd export | git hash-object -w --stdin)
tree=$(printf '100644 blob %s\tissues.jsonl\n' "$blob" | git mktree)
commit=$(git commit-tree "$tree" -m "beads snapshot")
git push --no-verify --force origin "$commit:refs/beads/snapshot"
```

Три подробности здесь не косметические, каждая куплена находкой ревью
(codex, 2026-08-29), и две из них проверены экспериментально.

**`--no-verify` на внутреннем push обязателен.** Без него `git push` внутри
`pre-push` заново запускает `pre-push` — рекурсия без дна, и на каждом витке ещё
и `bd dolt push` по общему для всех worktree `.dolt/noms/LOCK`. Измерено в
одноразовом репозитории: без флага хук отработал 5 раз и остановился только
предохранителем, с флагом — один раз.

**Снапшот публикуется ДО `push_beads_state`, а не после.** `pre-push` работает
под `set -e`, а `push_beads_state` намеренно возвращает ненулевой код при
настоящем отказе `bd dolt push`. Значит строка после него не выполнится — и не
выполнится ровно в том сценарии, ради которого страховка существует: `bd dolt
push` упал, история на remote под вопросом, здоровая копия есть только локально.
Порядок «сначала спасти копию, потом рисковать» — единственный, при котором
страховка вообще срабатывает.

**Remote — всегда `origin`, а не аргумент `$1`, который git передаёт хуку.**
Иначе `git push fork feature` уложит снапшот в `fork`, а канонический
`origin/refs/beads/snapshot` останется старым, и восстановление из README будет
читать устаревшую копию, не зная об этом. Если remote `origin` в клоне нет —
тихий выход, как при отсутствии `bd`.

Таймаут нужен и вокруг `bd export`, и вокруг внутреннего `git push`: SSH-remote,
ждущий интерактивной аутентификации, иначе задержит push бессрочно — то есть
страховка нарушит собственное обещание никогда не блокировать.

**Почему хук, а не GitHub Action.** Риск из `nocx-wj4` — это подвисшая история
именно в `refs/dolt/data` на remote. CI умеет читать только remote, то есть в
тот единственный момент, ради которого страховка существует, он забэкапит ровно
сломанное состояние. Здоровая копия в этот момент лежит в локальной Dolt-базе
разработчика, и `pre-push` — единственное место, откуда до неё есть доступ.
Побочно: не нужно ставить `bd` и бутстрапить базу на раннере.

**Почему реф, а не ветка.** `refs/beads/snapshot` не показывается в списке
веток, не участвует в PR, не клонируется по умолчанию — ровно как уже живущий
на том же remote `refs/dolt/data`.

**Failure policy — как у `pull_beads_state`, не как у `push_beads_state`:**
только WARN, push не блокируется никогда. Страховка, которая ломает push, будет
обойдена через `--no-verify`, и тогда её нет вовсе. `bd` отсутствует или
возвращает 3 — тихий выход 0, как во всех остальных функциях этого файла.
`timeout -k` — по образцу соседей, по причине из `nocx-v48vl`.

**Восстановление** (в README, дословно) — проверено сквозняком 2026-08-29,
2720 иссуев вышло, 2720 вернулось, id сохранены:

```sh
git fetch origin refs/beads/snapshot:refs/beads/snapshot
git cat-file -p refs/beads/snapshot:issues.jsonl > .beads/issues.jsonl
sed -i '/^sync\.remote:/d' .beads/config.yaml
bd init --from-jsonl
```

Не `bd bootstrap`: проверено `--dry-run`, отвечает «clone from remote», его
порядок (sync.remote → `refs/dolt/data` → backup → JSONL) до JSONL не доходит,
пока remote настроен. А снапшот существует ровно для случая «remote отвечает, но
испорчен».

Не `--discard-remote`: снять `sync.remote` заранее говорит то же самое, но не
взводит следующий `bd dolt push` на history-replacing force-push. Первая версия
этой спеки предписывала `--discard-remote`, и это было неверно дважды — флаг
разрушительнее необходимого, а в неинтерактивном режиме он ещё и требует токен
`DESTROY-<issue-prefix>`, где префикс свежий `bd init` берёт ИЗ ИМЕНИ КАТАЛОГА, а
не из восстанавливаемых данных. Восстанавливаться надо в каталог с именем `nocx`,
иначе новые иссуи начнут называться `<dirname>-<hash>`.

Процедура проверяется дословно, а не пересказом: команда, которую невозможно
выполнить копипастой, — это не процедура восстановления.

**Паритет по содержимому.** `bd export` без флагов не включает memories.
Сегодняшний трекнутый файл — тоже, так что это паритет, а не регресс. Вопрос
«бэкапить ли memories, раз этот снапшот теперь и есть страховка» отдельный и
решается отдельным бидом, а не попутно.

### 3. Документация

- `AGENTS.md:23` — `.beads/issues.jsonl` больше не «passive export that may lag»

- `AGENTS.md:28` — блок «**Never resolve a conflict in `.beads/issues.jsonl` by
  hand**» удаляется целиком, вместе с абзацем про merge driver и `make hooks`.
  Вместо него одна фраза: файла в git нет, бэклог живёт в Dolt, снапшот — в
  `refs/beads/snapshot`, восстановление такой-то командой.
- `README.md:165` — «which the pre-commit hook then commits» больше не верно.
- `README.md:230` — описание порядка `bd bootstrap` дополняется тем, что
  трекнутого JSONL в этом клоне нет.
- `README.md:255` — «It then writes `.beads/issues.jsonl` and stages it»
  удаляется, вместо него описание снапшот-рефа и команда восстановления.
- `.beads/config.yaml:47-60` — **функциональная правка, не только комментарий.**
  Там стоит `git-add: true`, то есть `bd` стейджит файл сам, мимо хука; оставить
  это значит получать `git add` на игнорируемый путь при каждой записи в базу.
  `auto` и `git-add` переводятся в `false`: единственная причина держать экспорт
  в шаге с базой — что файл трекался, и она исчезает. `import.path` остаётся как
  есть — он нужен процедуре восстановления.
- `.githooks/pre-push:62` и `.githooks/beads-hook.sh:66` — оба комментария
  ссылаются на tracked JSONL как на fallback для `bd bootstrap`. После untrack-а
  это ложь, по которой следующий человек будет диагностировать восстановление.

Managed-блоки «Architecture in one line» в `AGENTS.md`/`CLAUDE.md` не трогаем —
их генерирует `bd`. `.internal/HANDOFF-2026-08-18.md` не трогаем — это
датированный хэндофф, исторический документ.

## Приёмка

Критерий 1 — тот, которого не было в `nocx-prz9`, и единственный, который
описывает поведение GitHub:

1. Две ветки, обе с изменением бэклога, мержатся чисто **без сконфигурированного
   драйвера**: `git -c merge.beads-export.driver=false merge-tree --write-tree
--name-only A B` не печатает ни одного CONFLICT. Сегодня этот прогон красный
   на парах вроде PR #129 и зелёный локально — расхождение и есть баг.
2. `git log --stat -1` нового коммита не содержит `.beads/issues.jsonl`;
   `git status` после коммита чистый (файл проигнорирован, не «untracked»).
3. После `git push`: `git ls-remote origin refs/beads/snapshot` непустой, и
   `git cat-file -p <sha>:issues.jsonl | wc -l` совпадает с `bd export | wc -l`.
4. Сквозное восстановление: во временном клоне без доступа к `refs/dolt/data`
   три команды из README дают рабочую базу с тем же числом иссуев, что
   `bd list --status all | wc -l` в исходном клоне.
5. `bd` не на PATH → `git push` проходит без ошибки и без стоп-сигнала.
6. `bd export` падает (симулировать шимом, возвращающим 1) → push проходит,
   печатается WARN.
7. В свежем клоне после `make hooks` `git config --get merge.beads-export.driver`
   пуст; в клоне, где драйвер был настроен, `make hooks` его снимает.

## Осознанно вне scope

- **Гонка двух worktree за реф не сериализуется.** Worktree A экспортирует
  состояние S1 и задерживается; B экспортирует S2 и делает force-push; A
  просыпается и кладёт S1 поверх. Tip рефа оказывается старее базы. Не чиним: это
  запасная копия, следующий push любого worktree её выправляет, а межпроцессный
  лок добавил бы отказ ровно в тот код, который обязан никогда не блокировать push.
  Записано, чтобы следующий читатель не принял это за недосмотр.
- **Локальный dangling-коммит снапшота не защищён от `git gc --prune=now`.**
  Проверено вручную: между `commit-tree` и `push` конкурентный `gc --prune=now` в
  соседнем worktree (общий object store) объект снесёт, и push упадёт — WARN и
  ничего больше. Авто-gc держит двухнедельный grace period и в это окно не попадает.
- **CI не зеркалирует снапшот.** Генерировать его в CI бессмысленно (см. выше), но
  зеркалировать уже опубликованный реф во внешнее хранилище — осмысленно. Отдельная
  задача, не эта.
- **История не переписывается.** 6.6 MB × N коммитов остаются в git-объектах.
  Rewrite публичного `main` несоразмерен выигрышу.
- `bd dolt push` / `bd dolt pull`, `post-merge`, `post-rewrite` и merge slot не
  трогаем.
- Мержи PR на локальные не переводим.
- Memories в снапшот не добавляем (отдельный бид, см. выше).
